# docs/ — як тут усе влаштовано

Документи в репо, поруч із кодом, змінюються через PR. Агенти не читають усе підряд:
вони йдуть через `INDEX.md` (генерується) і відкривають лише релевантне, починаючи з рядка `TL;DR:`.

## Де фіксувати продуктову логіку

Numio не потребує Swift Evolution-процесу для своїх CLI-фіч: він охоплює зміни визначених частин самого Swift-проєкту — мови, стандартної бібліотеки, окремих core-бібліотек та інтерфейсів основних інструментів на кшталт Swift Package Manager — через публічні пропозиції й review спільнотою та рішення evolution workgroup. Для Numio корисний принцип — явно описати наслідки зміни до реалізації; масштабну процедуру review переносити не потрібно.

1. **Issue** — проблема, людський DRI, межі задачі та приклади для конкретної зміни. Для малої задачі issue достатньо як brief.
2. **Spec** — довготривалий контракт поведінки: допустимий ввід, результат, помилки, граничні випадки та нерозв'язані питання. У `docs/specs/time-grammar.md` приклади мають розрізняти бажаний результат від того, що CLI фактично робить зараз.
3. **Tests** — executable-перевірка прийнятих прикладів зі spec. Зміна реалізації не приймає відкриті продуктові рішення автоматично.
4. **ADR** — коротке пояснення важливого, довготривалого архітектурного чи продуктового вибору: чому його зробили і які альтернативи відкинули. Не дублюй у ADR таблицю поведінки зі spec.
5. **Pitch** — гіпотеза про користувача, проблему та напрямок продукту до того, як вона стала конкретною задачею.

Відкриті питання зі spec залишаються відкритими, доки людський DRI явно не вибере поведінку. Позначай ADR як прийнятий лише після такого рішення. Swift API коментарі можуть пояснити використання типу чи функції, але не замінюють CLI spec.

Офіційний опис [Swift Evolution](https://www.swift.org/swift-evolution/) і його [процесу](https://github.com/swiftlang/swift-evolution/blob/main/process.md); [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/) стосуються ясності Swift API, а не повного продуктового контракту CLI.

## Типи документів
| type | де | що це | живе |
|---|---|---|---|
| pitch | `pitches/` | проблема, appetite, ставка (PR/FAQ-lite) | до рішення, потім історія |
| adr | `decisions/` | важливе рішення та його rationale | поки актуальне; superseded/rejected зберігають історію |
| spec | `specs/` | очікувана поведінка, приклади для тестів | живий |
| initiative | `initiatives.md` | що в роботі, хто DRI | живий |
| eval | `evals/` | перевірка конкретного питання, коли вона потрібна | за потреби |
| guide | `guides/`, `operating-model.md` | короткі правила, що реально використовуються | поки актуальне |
| brief | `briefs/` | задача для агента (не індексується) | тимчасовий |

## Обов'язковий frontmatter
```
---
id: ADR-0005            # унікальний
title: Коротка назва
type: adr               # pitch | adr | spec | initiative | eval | guide
status: proposed        # adr: proposed|accepted|superseded|rejected; pitch: proposed|bet|shipped|killed;
                        # spec: draft|accepted; initiative: active|parked|done
date: 2026-10-01
modules: [NumioCore]    # опційно, лише inline-списки
tags: [parsing]         # опційно
owner: ім'я             # опційно, людина (DRI)
supersedes: ADR-0002    # опційно
---
TL;DR: одне речення одразу після frontmatter.
```

## Правила
1. Один документ — одна мета. Посилайся на інші за `id`, не копіюй текст.
2. `TL;DR:` обов'язковий, перший рядок після frontmatter.
3. Прийняті ADR не переписуємо заднім числом: за потреби позначаємо їх `superseded` або `rejected`. Неактуальні чернетки, дублікати та невикористовувані process-доки можна видалити після перевірки посилань.
4. Після змін: `python3 scripts/build-index.py`. У CI: `python3 scripts/build-index.py --check`.
5. Мова: документи можуть бути українською, ключі frontmatter завжди англійською.
